# J5: the intent registry, pack intent kinds and program seats

Status: done, kernel half (19 Nov 2026). Kernel track. Design: `handover/design/SSE4-record-logic-programs-design.md`, sections 6 and 9 (Care 3), and section 10 row J5.

## What was built
**`sse_trigger::intents`.** The intent list is no longer a UI-only TypeScript union. It is a registry the kernel knows.

**Built-in kinds** (Rust, the same fields as `packages/ui-contract/src/intent.ts`):

| Kind | Applied by | Notes |
|---|---|---|
| `set_value` | the kernel | Becomes `set_authored`. |
| `adopt_physics` | the session | Never applies without the GM. |
| `stack_packs` | the session | Never applies without the GM. |
| `scan_toggle` | the kernel | Never applies without the GM. |
| `grant` | the kernel | Never applies without the GM. |
| `add_note` | the kernel | New. A note to the seat's own audience (its journal) applies at once (design 2); any other note asks the GM. |

- The two session kinds need the session's pack stack, so the session keeps applying them.
- The translation to kernel requests (`to_request`) is the chart room's `intentToRequest`: `at_yr` is rounded like `Math.round` and multiplied by 31 557 600 s.

**Pack kinds** come from `provides.other.intents`:
- Shape: `{kinds: [{kind, meaning, fields: [{name, type, required?}], subject?, valid?, never_auto?}]}`.
- Field types are `text`, `number`, `bool`, `address`, `list` and `any`.
- `subject` defaults to the `address` field.
- `valid` is a K8 condition. It reads the subject's facts, kept values and tags, with the payload as `intent.<field>`, and is checked for every seat.
- An applied pack intent is written to the record as `intent.<kind>`, from `seat.<id>`. J4's `on_intent` rules take it up there.
- **Refused at load:**
  - a duplicate kind or a built-in's name;
  - a reserved name (`proposed`, `decided`, `seats`);
  - a bad identifier or an unknown key;
  - a `subject` that is not a declared address field;
  - **a rule that listens for (`on_intent`) or sends (`send_intent`) an undeclared kind, or a built-in kind.**

**Seats.**
- A seat has the shape of `seat.ts`, plus `program` (J6). The chart room's own fields (`sealed`, `screens`, `lens`) ride through untouched.
- The plan is a GM-only record event (`intents.seats`); the latest plan wins.
- With no plan set, the seats are the GM and the shared table. A GM seat is always present and may send every kind, the pack kinds included.
- `set_seats` refuses unknown kinds, auto-approve without `may_send`, duplicate ids, and a program seat with GM authority.

**`decide`** is the chart room's rule, checked in this order:
1. Malformed: refused, with `checkIntent`'s words.
2. Not in `may_send`: refused.
3. Not valid now: refused.
4. GM: applied.
5. A player setting `observe.*`: refused.
6. A `never_auto` kind: asks the GM.
7. Inside an `auto_approve` scope (address segments) and its fields: applied. Otherwise it asks the GM.

**Program seats are stricter:**
- an intent whose subject lies outside every `auto_approve` scope for that kind is **refused**, never queued;
- a session kind is refused.

So a program cannot do anything outside what the GM attached it for.

**The GM queue** is `intents.proposed` and `intents.decided` record events, a fold that replays. The `intents.` prefix is plural so it never matches `on_intent`. Each intent is answered once, and a yes cites the proposal.

**Kernel ops** (GM machine only):
- `intents`: the kinds, the seat plan and the pending intents;
- `set_seats {seats, at_s}`;
- `send_intent {seat, intent, at_s, check_only?}`: decide, then apply, queue or refuse. A built-in's response is in `applied`. `check_only` writes nothing;
- `intent_decide {proposal, approve, at_s?}`.

**Fixture packs:** `tests/fixtures/packs/rpg-intents.json` adds `hail` (valid only on a subject tagged `crewed`) and a rule `answer-hail` that notes the answer. The shared approval cases are in `tests/fixtures/intents/decide-cases.json` (16 cases).

## Limits and next
- **The chart room still uses its own `INTENT_KINDS` and `decide`.** Switching it to the `intents` op and `send_intent` is a UI-track step. The parity test keeps the two in step until then, and a new built-in must be added to both until the switch.
- A pack intent's effect is whatever rules do with `intent.<kind>`. Held orders and turns (design 7) come later.
- `send_intent` runs on the GM machine. A player seat's intent still reaches it through the session's peer-to-peer path, as now.
- Programs (J6) drive seats with `program` set and send through `send_intent` with the same checks.
