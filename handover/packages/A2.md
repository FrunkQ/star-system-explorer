# A2: Orac, change requests (part 1: the loop; physics, lenses, atom issues)

Status: parts 1 to 3 done (19 to 21 Nov 2026, agents track). Next: boxes (J3) and game tables as pack data.

## What was built
- **The loop** (`packages/agents/src/loop.ts`), in the shape of Ovid Next's builder (`agent/builder.ts::buildFlow`):
  one fixed system turn (cacheable), one request turn, then rounds. Each round the model either asks to read
  catalogue entries (`{"need": [...]}` or `{"find": "..."}`, a lookup, at most three, not counted as a try) or answers
  with one JSON object `{note, make: [{kind, title, rationale, doc}], missing}`. Every made thing is checked by the
  host's own validator; every problem goes back at once; up to three fixes. A run limit in dollars stops before a call
  that would pass it. The result splits **passed** (offered for acceptance) from **failed** (shown with problems, never
  with an Accept button). The loop applies nothing.
- **Orac** (`orac.ts`): standing instructions (real physics, smallest change, never invent a node, parameter, layer or
  field; "missing" entries for what SSE lacks), the request turn (what is open now, labelled as data, then the GM's
  words), the catalogue lookups (Ovid's Bibliotheca: keyed one-line entries, full entry on request), `runOrac`, and
  `oracMay` (GM seat only: authority gm and audience all).
- **Targets** (`orac-targets.ts`), each checked and accepted through the GM's own path, with no validator of Orac's own
  where SSE has one:
  - `physics`: a parameter change to a flow in the stack. Checked by the kernel through `previewRequest` (the scratch
    kernel loads the candidate campaign pack); unknown nodes and parameters, non-numbers and no-op values are refused
    first, naming what exists. Accept files it on the Physics screen as an Orac request (status draft): the GM sees its
    diff and effect there and adopts or declines it as any other request.
  - `lens`: checked by `checkLens`, plus a new `mine.*` id that is not taken and card fields that exist for that kind.
    Accept saves it with the GM's lenses and switches to it.
  - `atom_issue`: a missing physics block in the issue-spec-test-code form; every reference needs a DOI or an https
    address. Accept opens GitHub's new-issue page with the draft filled in (label `atom`); nothing is sent until the GM
    presses Submit there.
- **Catalogue**: every flow in the stack (`flow:<id>`: nodes, atoms, parameters with values, wires, publishes), every
  lens (`lens:<id>`) and the card fields per kind (`fields:<kind>`).
- **Panel** (`OracTab.svelte`, Agents, Orac tab): ask in a sentence; the first try's estimate; the tries as they happen
  (read the catalogue; problems sent back; passed); the result with calls, tokens and cost; one card per passing draft
  with its summary, rationale and Accept; failing drafts dashed, with their problems and no button; "What SSE does not
  have yet". The shell builds the targets (`App.svelte`, `oracHost`) and offers Orac only on the GM seat.
- `asker` in `agents.ts`: the loop's model call goes through `chat`, so every try is estimated, cleaned of keys, held to
  the day's cap and written to the ledger (failed calls too).

## Acceptance (build plan A2: invalid candidates never reach the accept button; nothing mutates without accept)
| Criterion | Where it is proved |
|---|---|
| Invalid candidates never reach Accept | `packages/agents/test/orac.test.ts` (real kernel): a draft with redistribution 7 is rejected by the kernel, its words ("value 7 is outside the allowed range 0.25 to 0.666…") go back to Orac, the fix (0.5) passes and is the only one offered. A draft still wrong after three fixes ends in `failed` with no value to accept. Lenses with an unknown layer, a taken or non-`mine.` id or a field no planet has, atom issues with a reference lacking a DOI or address, and an unknown kind are all refused. Browser (`tests/ui/orac.e2e.mjs`): no failed card is shown with a button; one passed card has Accept |
| Nothing mutates without accept | Same Node test: after the run the workspace has no request, the state hash and stack hash are unchanged; after Accept the request is filed as a draft (not adopted) and the stack is unchanged. Lens saved and issue opened only on Accept. Browser: the state hash is unchanged through the run and after Accept; the request appears on the Physics screen for the GM to adopt |

Also: lookups do not use up a try; a run limit stops before a call that would pass it; Orac refuses a player seat.

## Honest limits
- Orac's catalogue lists parameter values but not their allowed ranges (U3 kernel gap 2: no op describes atoms). Orac
  learns a range from the kernel's refusal and fixes it in the loop, as the test shows; an `atoms` op with ranges would
  save a try.
- Physics edits are parameter changes only (as the GM's own editor); adding or rewiring nodes waits for the editor.
- Tested against scripted mock providers. Real models vary: a small local model may need all three fixes or fail to
  write valid JSON. No model has been measured for the Building job yet (`picks.json`).
- The estimate shows the first try only; each fix sends the whole conversation again (as Ovid's estimate warns).

## Part 2: how SSE looks and what players learn (`orac-looks.ts`)
Each target uses the checker of the GM's own editor and accepts through the GM's own path:
| Kind | Check | Accept |
|---|---|---|
| `style` | `checkStyle` with the draft in the registry: the view's schema, ranges, `extends`, promoted settings, cost against this device's tier; new id `mine.*` | kept with the GM's styles (`StylesHost.keep`) |
| `screen` | `checkScreen` (views, areas, settings, styles, data view) plus theme, symbology, vocab and a player audience; new id `mine.*` | handed to the players page on this device, as the composer's Show to players |
| `symbology` | `checkSymbology` (channels, sources, colours, inheritance and mixing); new id `mine.*` | kept with the GM's symbols (`SymbologyHost.keep`); chosen on the Symbols screen |
| `data_view` | `checkSetup` on the campaign's setup with the view added (never the GM-only tier, unique id, known tiers), and every override names a field or tag in the disclosure map | `applySetup`: the campaign's player-data pack, chronicled as a stack change |

Physics catalogue entries now carry each parameter's meaning, unit and allowed range from the kernel's `atoms` op
(`Session.atoms`, `loadAtoms`), so Orac drafts inside the ranges instead of learning them from refusals.

Catalogue entries: `view:<id>` (every setting with type, range, default, unit, cost and meaning), `style:<id>`,
`symbology:<id>`, `disclosure` (each field and tag at its tier) and `data_view:<id>`.

Found on the way: an accepted value came out of the tab's component state as a deep proxy, which `structuredClone`
(inside `playerDataPack`) refuses, so the apply silently never happened. The tab now hands targets plain data and shows
any thrown error as "Not applied: ...". The browser test covers it.

Proved by `packages/agents/test/orac-looks.test.ts` (each checker's refusals, nothing kept or applied before accept, a
screen draft fixed in the loop) and `tests/ui/orac.e2e.mjs` (a data view with a GM-only tier sent back, the fix applied to
Player data only on Accept).

## Part 3: programs (J6), `orac-rules.ts`
- `program`: a J6 `ProgramDoc` (states with an optional pick over what the seat has sensed, one intent each,
  transitions in the K8 condition language). The check puts it in the campaign's own programs pack
  (`campaign.programs`) and tries the whole stack on the scratch kernel (`session.trial`), so every J6 load refusal comes
  back in the kernel's words (an undeclared intent, a transition to an unknown state, `{pick}` with no pick...); an id
  already in the stack is refused first. Accepting stacks that pack (`stackPacks`, chronicled as a stack change); further
  programs go into the same pack. Nothing runs until the GM attaches the program to an object whose template lists it.
- Catalogue: `intents` (each declared kind with its meaning and fields), `program:<id>`, `template:<id>`; the form carries
  the condition language.
- Proved by `packages/agents/test/orac-rules.test.ts` on the real kernel with the `rpg-programs` fixture.

- `sifter` (21 Nov): a story-finder sifter. The check runs it once inline through the kernel's `sift` over the campaign
  (GM side, read only; a malformed one comes back as `bad_sifter` in the kernel's words), then tries the stack with it in
  the campaign's own sifters pack (`campaign.sifters`). The accept card says how many hits it has now. Accepting stacks
  that pack, so the story finder and Minerva (over her audience's scene only) use it. Catalogue: `sifter:<id>` for the
  starters and the stack's sifters. Proved in `orac-rules.test.ts` (Kestrel: "a crowded world" finds Tarn once).

## Part 4: boxes and game tables, `orac-blocks.ts` (21 Nov)
- `box`: a J3 `BoxDoc` (several atoms or boxes wired together and used as one block). The check puts it in the campaign's
  own boxes pack (`campaign.boxes`, `provides.boxes`) and tries the stack on the scratch kernel, which compiles the box
  (an unwired port, an unknown atom, a box inside itself) and runs its own worked examples, refusing in its own words.
  An id already used by a box or flow is refused first. `format` and `version` default to `sse.box/1` and `1.0.0`;
  `explain` needs all of curious, science and formula (the kernel says "missing field").
- `table`: a game's lookup table as a class atlas scheme (one base class per row, a region over named axes), the same
  mechanism the Traveller pack's codes use. It goes into `campaign.tables` (`provides.other.schemes`, `axes`,
  `classes`); the kernel's atlas load refuses an unknown axis, a parent cycle, a class with no bands and an id defined
  twice. A class filed under another scheme is refused before the kernel sees it.
- Catalogue: `box:<id>`, `axes` (each axis with the fact it reads and its unit), `scheme:<id>` (its classes as rows).
- Proved by `packages/agents/test/orac-blocks.test.ts` on the real kernel (an Earth box with g and escape velocity; a
  light, standard and heavy gravity table over the base atlas's `gravity` axis; Orac's loop fixing an unknown axis).
- Preview (21 Nov, kernel `classify_preview`, PR 73): after the trial passes, the check asks the kernel to label the
  campaign's bodies under the candidate stack (GM side, read only, nothing loaded). The accept card says how many land
  in each row and how many fit none. A row whose own `examples` disagree with it is refused with the kernel's line.
  With no universe open the preview is skipped. `Session.classifyPreview` carries the op.
- Limits: overlapping rows are not refused at load (the base atlas's own tests check that). The kernel counts as a body
  only an address with `body.kind` or `body.mass`, so a campaign of authored player facts alone (like Kestrel's
  `kind`) shows "no body has the facts to place yet".
