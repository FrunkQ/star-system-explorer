# V13 (part 1): Make a system, by importing a V3 save or growing a new one

Milestone M2 asks to "import a V3 system, edit it on the chart, ask why". This part builds the import and generate screens over the physics track's kernel ops (`import_v3`, `run_formation`; `handover/packages/K-physics-ops.md`). Both ops are pure, so everything here is a **preview**: the campaign's universe and state hash do not move.

The branch merges PR 4's branch (`claude/project-thread-h9y77o`, commit bc6f33a) to get the ops. PR 5's branch conflicts with PR 4 in kernel files. The kernel or physics thread is asked to combine them; the UI track does not resolve kernel code.

## What landed

- **Session** (`packages/ui-contract/src/session.ts`): `importV3(save, {universe_id?, reconstruct?})` and `runFormation(req)`. Both are GM only, and both return the kernel's result or its error code.
- **`packages/ui-contract/src/make.ts`**:
  - kernel shapes the screens read (`V3Imported`, `ImportReport`, `FormationRan`, ...);
  - `importedSystems`, `sceneFromImport` (values are the save's own, marked authored and imported; honesty marks become the "impossible" stamp);
  - `reportSummary`;
  - `sceneFromFormation` (the star at the system's age from the nearest history slice; each world with orbit, mass, radius and surface temperature from S0; formation events on the ruler's list);
  - `worldWords`, and `noWorldsWhy` for runs whose disc was stripped.
- **`packages/shell/src/MakeSystem.svelte`**: the "Make a system" link on the status bar opens a dialog with two tabs.
  - **Import a V3 save**:
    - a file input; a `.sse.zip` is refused with "unpack it first";
    - "Try a sample save" (the synthetic Sol fixture, copied to `public/samples/` by `build-shell.sh`);
    - a summary in words, then the recomputed-against-V3 table with the differing rows marked;
    - what was kept, set aside and dropped, and a download of the full report;
    - a picker when a starmap holds several systems.
  - **Grow a new system**: seed, optional star-mass pin, and the formation rule (modern, classic Accrete, corrected). It reports the worlds in words, the pipeline's notes and "How it formed".
  - **Preview**: the ordinary system chart and body card modules, mounted on their own workspace in view mode, so they cannot edit.

## Evidence

- **`packages/ui-contract/test/make.test.ts`** (2 tests):
  - the sample save imports, with Sol, its 4 subjects with kinds, Earth at 1 AU and 1 M⊕, and age 4.57 Gyr;
  - the Moon carries its honesty mark, and the report reads 1 differing and 5 within;
  - a non-save is refused with `import_failed`, and a player seat is refused;
  - the same seed gives the same scene, and a bad rule is refused;
  - neither op moves the state hash.
- **`tests/ui/make.e2e.mjs`**:
  - a non-save is refused in words;
  - the sample report and preview work, and choosing Earth shows 1 M⊕ on the card;
  - "first light" grows 8 worlds in the browser, the same as Node;
  - the state hash does not move;
  - at phone width (390 px) the dialog does not overflow.
- Screens: `V13-screens/`.

## Not done, and why

- **Adopting**: done in part 2, below.
- **`reconstruct`** (candidate histories for an imported system) is supported by the session but not offered on screen yet. It is heavy, so it should go behind the device tier.
- **Inheritance from a cosmos birth or a patch envelope, and per-world pins**, are not on the form yet. Seed, star mass and rule are.
- **Generated worlds have no albedo**, so the Light switch shows them only by their own heat. That is honest, not a bug.

## Part 2: adopt into the campaign (19 Nov, UI track, on kernel commit 38d0cc1)

What it does:
- **"Add to the campaign"** under a preview (Make a system). It calls the kernel's `adopt` op with the same save text or the same formation request the preview used. A grown system's address is `<campaign root>/sys:@<seed slug>` (the preview runs at that address too, so the preview and the adopted system are the same system; the same seed lands in the same place). The state hash moves, the history ruler gets the events, and adopting the same system twice is refused in words ("already in the campaign").
- **The chart reads it back from the universe.** A status-bar control "On the chart" lists the campaign's own system and every adopted one. An adopted system is drawn from `resolved_system` (`sceneFromResolved` in `ui-contract/src/make.ts`), not from the preview: facts, kernel's names (`v3.name`), S0 surface regimes. The chart switches to view mode and What-if is hidden there (what-if edits are the fixture campaign's derivations).
- **Look ahead on an adopted system** uses the kernel's own `spec` from `resolved_system` (the panel says "the system as the universe holds it") instead of building one from the chart. "Keep and move now" sends `write_back: true`; the kernel writes one `time.aged` event and the chart reads the aged star back (Sol at 10 Gyr: luminosity 2.43 L☉, radius 1.66 R☉, 5590 K). The status line says the star and orbits are written back; the ruler shows the "aged" event.
- **Honesty** (updated after kernel 7c1ed04). Each value is marked by the evidence `resolved_system` now returns per fact: authored (and authored-impossible) as "set", catalogued as catalogued, a grown system's values as resolved, a written-back value as derived (by `time.aged`, so the card says "aged by a kept look-ahead"). Subject stamps follow the physical values' classes; V3 bookkeeping (`v3.name` and so on) does not count, except V3's overrides and anomalies, which carry the impossible mark.
- **The "On the chart" list comes from the kernel** (`systems` op) when the campaign opens, not only from this session's adoptions. Note: the browser does not keep the universe across a reload yet (nothing in the shell persists the chronicle), so after a reload the list is empty because the universe is; once a campaign is saved and reopened, the list fills from it.

Session: `adopt(source, occurred_at_s?)`, `resolvedSystem(system, at_s?)`, `listSystems()`, `commitLookAhead(branch, move_now_myr?, write_back?)` (returns `aged_event`, `aged_at_myr`).

Checks: `ui-contract/test/adopt.test.ts` (grown system adopts as one event, reads back with the preview's orbits and age, refused twice; Sol adopts by evidence class and reads back with its names; look-ahead from the resolved spec with write-back raises the Sun's luminosity read back, values marked derived). `tests/ui/adopt.e2e.mjs` (grow, add, chart shows the same worlds from the universe; refused twice; add the sample save; look ahead on Sol to 10 Gyr and keep with move-now; the Sun read back has aged; back to Kestrel Reach). `make.e2e.mjs` now grows at the seed's campaign address. All in `npm run ui:e2e` and CI. Screens: `V13-screens/v13-adopted-grown.png`, `v13-adopted-aged.png`.

### Still open
- **Saving a campaign** in the browser (the chronicle across reloads) is not built; it is what makes adopted systems outlive the page.
- **Editing an adopted system** on the chart: its facts are read back as not editable. Edits through `set_authored` on its addresses work in the kernel; the card needs field parsers for SI facts first.
- **Kept look-ahead on the fixture campaign** (Kestrel Reach) still does not rewrite orbits: Kestrel's chart is derived from the fixture scene, not from `resolved_system`.
