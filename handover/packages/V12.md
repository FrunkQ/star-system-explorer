# V12: symbology (diagrammatic and colour-coded grammars, mixing, legend, editors)

Status: done (18 Nov 2026), branch `claude/project-thread-adgixl`, on top of V2. Finished the same evening with V3's real colour table and the V3 colour import (section "V3 colours"), once the physics track brought `docs/v3-colours.json`.

## What was built
- **The symbology engine** (`packages/ui-contract/src/symbology.ts`, H8.4A). A symbology document (`sse.symbology/1`) binds facts to visual channels:
  - Sources: the object's kind, its C1 classes (`class`, base class first), a tag (`tag:<prefix>`) or a number (`number:<name>`).
  - Channels: shape, fill pattern, colour, size, outline, ring, glyph (a short class code) and ink tone.
  - Scales: a table (keys may end in `*` to match a prefix) or ordered thresholds; a fallback per binding.
  - `inherits` another symbology; `mix` takes whole channels from others; own bindings override per channel and kind.
  - `prefer` on a binding: sources tried before `from`, first match wins (V3's rule: a habitability tag before the class).
  - `legend`: the hand order of entries. `placeholder`: says which values are stand-ins (none ship now). `tag_colours`: tag category colours for tag chips (from a V3 save), never a mark.
  - `checkSymbology` refuses bad channels, bad sources, colours that are not `#RRGGBB` or `palette:N`, and inheritance loops.
- **Theme capability rules** (`markerFor`). The theme says what it can carry (`supports`); a stated rule collapses the rest, and the rule's words come back as `marker.collapse` for the key:
  - One colour: if the symbology binds no fill pattern, each colour becomes a pattern in a fixed order (solid, hatch, stipple, band, cross, grid, dash, hollow); otherwise colours are dropped. Bindings marked `when: "one-colour"` (class codes) then come into force.
  - No patterns: patterns become solid. No shapes: shapes become discs.
  - `palette:N` colours take the theme's own palette.
- **Three shipped symbologies**, generated by `scripts/make-symbologies.py` from the 65 base classes in `packs/sse3-classic` (C1), so every binding names a real class:
  - **Diagrammatic**: class family by shape and shading in one ink, plus a 2 to 3 letter code per class (the cartographer's key), so a one-ink chart tells every class apart. Families: rocky (solid disc), hot (hatch), chemical (dash), living water (band), ice (hollow), neptunes (cross), gas giants (stipple), substellar (solid diamond), built (grid square), unbound and young (solid triangle), small bodies (solid square). Ringed is a ring.
  - **Colour-coded**: SSE 3's own colours on plain discs (see "V3 colours"); its class codes appear only under a one-colour theme. Stars by spectral key (tag `spectral:<key>`), belts and constructs by kind.
  - **Shapes and colours**: inherits diagrammatic and mixes in the colour channel.
  - `symbology.names.json`: plain class names for keys, from the same pack.
- **Drawing** (chart grammar): `Mark.svelte` draws what the symbology returns (colour fill, triangle, ring, glyph, every pattern); `HatchDefs` gains grid and dash and a fine full-ink set of patterns for marks; `Legend.svelte` draws generated entries with the chart's own marks; `markExtent()` tells a view how far a mark reaches without the view knowing its shape.
- **The GM chart** asks `ctx.mark()` and shows a **Key** (collapsible, bottom left) generated by `legendFor` for the bodies on the chart, with the collapse rule when one applies.
- **Symbols screen** (`packages/views/symbols`, header "Symbols"):
  - Grammar picker with descriptions (and a warning if a document marks placeholder values).
  - "Colours from SSE 3" (collapsed): paste or load V3's palette overrides; read a V3 save (.sse.zip or starmap.json); a report says what landed where; tag colours show as chips.
  - Mix by channel: shape, shading, colour and code, each from either grammar or none.
  - Classes table (this chart's classes, or all 65): mark, name, shape, shading, colour swatch (`input type=color`), code.
  - Any change makes "Campaign symbols", inheriting the grammar in force; "Back to the shipped symbols" removes it.
  - Key for this chart and the same key under every shipped theme, drawn in that theme's tokens.
  - The choice and the edited copy are a device preference (`shell/src/symbols.svelte.ts`): symbols never reach the kernel.
- **Players' chart** draws marks too: `PlayerContext.mark` with `playerSubjectOf` (kind, recorded `class` fact, size class). The player page has a Symbols picker beside Theme. Kestrel's recorded facts gain `class` for Tarn and Vault, disclosed at `scanned`; both vocabularies word the class ids (`FieldWords.values`).
- **Kestrel's fixture scene** now tags bodies with C1 class ids (`class:planet/ocean`, `class:planet/ringed`, ...).

## V3 colours (finished 18 Nov, evening)
Source: `docs/v3-colours.json` and `.md` (physics track, read from V3 3.1.80 `colors.ts`, `tokens.css`, palette and tag stores).

- **Colour-coded is V3's table.** V3 colours a body by first match: habitability tag (`habitability/earth-like` or `/human`) blue `#007bff`; biosphere green `#00ff00`; brown dwarf `#5d4037`; ice giant `#add8e6`; gas giant `#cc0000`; else terrestrial `#cc6600`. Belts `#888888`, constructs `#ffd24d`, stars by spectral key.
- **How classes got their V3 colour (a reading, for Alex to check).** V3 gave a body several classes and matched literal ids ("classes contain gas-giant"). V4's C1 gives one base class, so `make-symbologies.py` gives each class the colour V3 would give a typical member: biosphere when the class's region requires a biosphere; else the first of brown dwarf, ice giant, gas giant whose core region holds the class's typical values (its own core midpoints when it lists none); else terrestrial. Result: 43 terrestrial, 14 gas giant, 3 ice giant (ice giant, sub-neptune, super-neptune), 2 brown dwarf (brown dwarf, ultra-cool dwarf), 3 biosphere (forest, jungle, swamp). So, as in V3, ice worlds, oceans, mini-neptunes, hot neptunes and super-puffs are orange, and earth-like worlds are blue only when tagged.
- **Honest consequence.** Colour now tells V3's eight groups apart, not all 65 classes. Under one-colour themes the class codes still separate every class; diagrammatic and the mix separate every class under every theme. The tests say exactly this.
- **Palette overrides** (V3 localStorage `sse-palette-overrides`, `{token: hex}`) are the viewer's, so they land on the campaign's edited symbology on this device, not in campaign data. `v3-colour-tokens.json` (generated) says what each token recolours: body tokens their classes, `--body-habitable` the habitability-tag preference, `--star-*` the spectral table, belt and construct by kind. Theme tokens (surfaces, text, accent) and other domain tokens (zones, hazards, bands) are left, each with its reason in the report. Paste the bare map, a localStorage dump holding the key, or load a file. A palette onto the diagrammatic grammar starts from V3's colours, so untouched groups keep theirs.
- **A V3 save** (`.sse.zip`, read with the platform's own inflate, or `starmap.json`/`system.json`): `coiCategories` (only categories the GM changed) become `tag_colours` on the campaign symbology; per-object colours are listed in the report by class: authored (fluid and life `colorHex`, biosphere `colorHex`/`lightHex`, construct `icon_color`, engine `exhaust_color_hex`) arrive with the save importer as authored facts; derived `apparentColorHex` is recomputed by V4. Skins (`sse-skin`, custom skins) map to V4 themes and are not imported here.
- **For the kernel track** (crates untouched here): `sse-import-v3` classes `apparentColorHex` as presentation (the colour note says derived) and does not know `coiCategories` (it would land as unknown). V3 tag chips are not drawn by any V4 view yet; `tag_colours` waits for them.
