# V4: peer-to-peer session (H9.2)

Status: done (19 Nov 2026), branch `claude/project-thread-adgixl`, PR into `main`. Alex lifted the pause (19 Nov, 00:11) and chose to put the player-join relay in the existing v4 Worker (decision card, 00:13).

## What was built
- **Protocol** (`packages/ui-contract/src/p2p.ts`, `sse.p2p/1`). The GM is the single writer. Messages: `hello` (a player asks to join), `manifest` (to one player: run id, kernel and app versions, universe, opening packs, the full event log, state hash, clock, granted data views), `event` (one applied intent with its event id and the state hash after it), `state` (session clock and granted data views), `beat` (heartbeat with sequence and state hash), `snapshot` (a player asks for the manifest again), `bye`.
- **Replication by intent.** Everything that changes the universe already goes through `Session.send` as an intent, so the GM's chronicle is the ordered list of intents its session applied. `GmHost` records it from the moment the campaign opens (before the recorded facts are entered) through a session hook; players replay each intent on their own kernel (Class A, bit-exact) and compare the state hash after every event. Stack changes travel with their packs. No kernel change was needed.
- **Session hooks** (`session.ts`, symbols not exported from the package index, so views cannot use them): `APPLIED` (watch applied intents), `REPLAY` (apply an intent the GM already applied, whatever the seat may send), `GRANT_VIEWS` (data views a player seat's screens may look through; before this a player seat could never name a data view).
- **`PlayerReplica`** states: joining, live, resync (a gap or a hash mismatch: asks for a snapshot and rebuilds a fresh kernel session), offline (no message for 6 s, or the GM's `bye`: read-only on the last state, back to live when the GM is heard), reload (protocol, app or kernel version differs: never drifts; the kernel version is checked right after the player's kernel starts).
- **Rooms (hubs).** `memoryRoom` (tests), `broadcastHub` (BroadcastChannel: other windows and screens of this browser), `relayHub` (WebSocket to the site Worker's room relay, reconnecting with backoff), `multiHub` (the GM serves both at once). A player tries the relay first and falls back to this browser after 3 s (`&via=browser` forces it).
- **Site Worker** (`worker/index.js`, `wrangler.jsonc`): serves `dist/` as before and relays `/signal/<room>?peer=<id>` WebSockets through one Durable Object per room (`SignalRoom`, SQLite class, hibernation API). The room adds `from`, delivers `to` messages to one peer and others to everyone else, announces leavers, caps rooms at 32 peers and 4 MB messages, and stores nothing.
- **GM shell**: "Share with players" in the status bar opens the players' screen in a new tab and shows the link, the number of screens and the event count; the clock follows the time ruler; all the campaign's data views are granted.
- **Players page** `players.html?join=<room>`: the table seat on its own kernel, a banner while joining, catching up, away (read-only) or needing a reload, and the state hash and route (relay or this browser) in the footer. The stand-in Scanned control shows only when the page stands alone.
- **App version** (`__SSE_APP__`, vite define): shell package version plus the commit (`WORKERS_CI_COMMIT_SHA`, `GITHUB_SHA` or git).

## Not done, and why
- **Direct WebRTC data channels.** The relay carries the session today (small JSON: events, a heartbeat every 2 s). The design's "P2P data channel with optional relay" can upgrade later: the relay already is the signalling path, so a WebRTC hub can exchange offers over it and fall back to it.
- Old player kernels are not stopped after a resync rebuild (one extra worker per resync).
- Player intents to the GM are V5; seats beyond the table are V10.
- Class B results (heavy blocks, LLM output) would travel as recorded chronicle data; none exist yet, so the log carries intents only.
