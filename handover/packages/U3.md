# U3: flow editor and explain mode with three lenses; change-request panel (without the agent)

Status: done (18 Nov 2026), branch `claude/project-thread-adgixl`, on top of U2. Decision record: `docs/adr/0006-physics-change-requests.md`.

## What was built
- **Physics screen** (`packages/shell/src/documents/physics.gm.json`): a second screen document for the same chart-room layout, switched from the header (Chart / Physics, key P; an icon button on phones). Flow editor in the chart area, change requests in the card area, the ruler as before. Both screen documents are checked before anything mounts.
- **Flow editor** view (`packages/views/flow-editor`): any flow in the loaded stack, drawn as ink on the chart ground. Flow inputs on the left with the real values of one body, atoms in columns by depth (`flowColumns`), published quantities on the right with their values now and, while a draft is open, the value with it ("→ 297.8"). Parameters are typed in place on their node; the drawing fits the room it has and scrolls on phones. The selected node explains itself in the three lenses.
- **Lenses** (`chart-grammar/src/Lenses.svelte`): Curious, Science, Engine as cumulative tabs (each adds to the one before, H6.5), arrow keys between tabs. Used by the flow editor and by every "why?" on the card.
- **Open the flow**: a derived value's "why?" now has "Open the flow" (GM seat, edit mode). It puts the flow on the bench with that body's inputs and the node that published the value selected.
- **Change requests** view (`packages/views/change-requests`): open requests (the GM's draft and Orac's), each with rationale, a diff of parameters (in force struck through, proposed in the accent), the kernel's verdict (Validated, or Rejected with the kernel's reasons), the effect on the bench's body (now, with it, change %), a reminder that the change applies to every body the flow serves, and Adopt / Decline. Adopted requests are listed "in force" with Withdraw; declined and superseded ones under Closed.
- **Orac without the agent**: `documents/orac.requests.json` holds a sample request in the shape Orac will file ("Keep the heat on the dayside": redistribution 1/4 to 1/2 for tidally locked worlds). It is marked as a sample on screen.
- **Contract** (`packages/ui-contract`): `physics.ts` (FlowDoc, PackDoc, ChangeRequest, editFlow, diffFlow, campaignPack, packFor, checkRequest, flowColumns, siText), `physics-edit.ts` (draftParam, previewRequest, adoptRequest, withdrawRequest, declineRequest, benchRef). Session: `stack()`, `flowDoc()`, `trial()`, a request queue, and the `adopt_physics` intent. Workspace: `screen`, `bench`, `requests`, `openFlow`, `fileRequest`, `notePhysics`.
- **Badge**: derived facts carry their publisher; a value published by the campaign pack shows "· changed physics" on its card field, the subject gets a "Changed physics" stamp, and the explanation shows the stamp too.

## Design sections implemented
H13 change requests (validated before display, diff with effects, nothing mutates without accept), H6.5 cumulative lenses, H8.8 builder tools are views that send intents (the flow editor and panel use only the session), K5 explicit `replaces` and one publisher per kind, H8.5 edit in place on phones too.

## Kernel gaps (reported to the coordinator, not worked around in /crates)
1. A stack change is not chronicled and the run manifest keeps the packs loaded at `open_universe`, so physics changes do not move the state hash and are not replayable. Wanted: an op (or `load_stack` behaviour) that records the stack change as an event and updates the manifest.
2. No op to describe atoms (ports, parameter declarations with ranges and descriptions). The editor learns a range only when the kernel rejects a value, and shows only wired ports.
3. Validation messages use Rust debug text (`Some((0.25, 0.666…))`); the UI rewrites it (`readable` in physics-edit.ts).
4. Explanations are by published quantity, so a node that publishes nothing cannot be explained on its own.
5. Flow `tests` are not run at `load_stack` (ADR 0006): when they are, edited flows need re-baselined tests.

## Known limits
- Parameter edits only; adding or rewiring nodes is later (the document model already carries it; `diffFlow` reports structure changes).
- One campaign pack; per-system or per-body physics is not modelled (a change applies to every body a flow serves, and the panel says so).
- Requests live in the workspace for the session; saving them with the campaign comes with campaign files.
- Undo (Ctrl+Z) covers value edits; physics changes are undone by Withdraw.
