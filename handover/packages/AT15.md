# AT15: wearing a kit (atlas design 11A.3, 11A.4 rule 5)

## Part 1 (25 Nov): control sets, one shared drawing, and the kit's screens

- **Control sets as data.** `ui-contract/src/atlas/controlset.ts`. A part declares a control as a kind: button,
  switch, choice, step, dial, tab or link (AT13). A control set says how each kind is drawn in a look:
  - `frame`: plain, bracket, pill, cap, ink or key.
  - `case`: as-written or upper.
  - `hotkey`: the key marked inside the word, as in `[P]RINT`.
  - `lit`: fill, invert, glow, underline or bold. This is how the control shows it is on, chosen or pressed.
- **Shipped sets.**
  - `plain`, the root: the chart room's own buttons.
  - `hauler`: brackets, capitals and keys, inverted when lit. Print reads `[P]RINT`.
  - `corporate`: glass pills that glow.
  - `deck`: console caps in capitals.
  - `guide`: gadget keys, with tabs and links inked.
- **Inheritance.** A set leaving a kind out takes its `extends` parent's drawing, then plain's, so a variant costs
  nothing.
- **Functions.** `drawingOf(set, kind)`, `controlWords(words, drawing, key)` and `checkControlSet(doc)`, which returns
  sentences, as the kit loader does.
- **Kits name their set.** `sse.kit/1` gains `control_set`: a set by id, or a set of the kit's own, which
  `checkKit` checks. The four starters name hauler, corporate, deck and guide. `controlSetOf(kit)` resolves it.
- **One shared drawing:** `chart-grammar/src/KitControl.svelte`, a new file agreed with the coordinator.
  - It draws any declared control in any set, in the look's tokens only.
  - Minimums no set can go under: a 44 px press target on touch (32 px with a mouse), the focus ring, and no motion
    under reduced motion.
  - Switches, choices and tabs carry `aria-pressed`. A set showing keys gets `aria-keyshortcuts`.
- **The Atlas part wears it.** With `ctx.control_set` set (a players' screen wearing a kit), its Contents, Back,
  Next and Print are KitControls. A set that shows keys answers P, C, N and B. Without it, the GM's chart room keeps
  the Atlas's own buttons.
- **`kitScreen(kit, situation)`** turns a kit's layout for a situation (after `extends`) into an ordinary
  `sse.screen/1` document, for the Run desk thread's players' screen. It returns null when there are no boxes: a
  holding card, or an unknown kit.
- **Agreed with the Run desk thread.**
  - The role card gets `Seat.kit` (a KitDoc id) and `Seat.palette`, travelling with the seat plan like the brand.
  - Precedence: a role's own Switchboard layout, then `kitScreen(kit, situation)`, then the Bridge.
  - The players' screen puts the resolved set on each part as `ctx.control_set`.

## Part 2 (25 Nov): the four kits on players' screens

The Run desk's wiring (PR 552 `Seat.kit` and `Seat.palette`, PR 556 `screenFor` and `ctx.control_set`) puts a kit's
layout on a role's screen. This part makes those layouts draw, and the role wear the kit's look.

- **The players' Atlas part:** `playerAtlas` in `views/atlas/src/index.svelte.ts` (`PlayerAtlas.svelte`), id
  `sse.view.atlas`, joined to `PLAYER_STACK` (one line in player-stack, invited by the Run desk thread).
  - Built from the scene the seat was sent, so a page holds only what that seat knows. No Edition switch and no
    "Seen by" (14A note 6).
  - Params: `edition` (a kit names it) and `page` (`selected`, the default, follows the screen's selection, so a
    chart beside it and the book move together; `contents` starts at the top).
  - Controls are the part's own (AT13): Back, Next, Contents, Print, all drawn by `KitControl` in
    `ctx.control_set`. A set that shows keys answers B, N, C and P. The Guide's edition keeps its device.
  - Pages: voice, letterhead (clearance is the seat's audience) and margin notes. Not yet on players' pages: the
    sources ("How we know" needs `known_to`, the GM's read) and the date (the player scene carries none).
  - In a narrow box (beside a chart, or a phone) the page folds to one column (`@container atlas`, 460 px).
- **`kitScreen` passes the kit's edition** to its Atlas parts, unless the layout names another. A kit item's
  `style` that is a shared view style (`wireframe`) is no longer written as a style document, which the screen
  refused ("no style wireframe"); it stays with the kit until the players' parts take a view style.
- **`resolveKit` kept `control_set` and `banners` out** of the resolved kit, so every role drew the plain set. Fixed,
  with a test.
- **The kit's look and palette on the players' page:** `shell/src/atlas/kitlook.ts`, used by `Players.svelte`.
  - The role wears the kit's look over the player's own theme (the Theme picker hides while a kit is worn).
  - One rule for every palette: the look's colours turn by the hue and saturation that take its accent to the
    palette's (lightness kept), then the palette's six checked tokens go on exactly, then the quiet structure they
    imply (pressed-control words in the ground's colour, focus in the accent, faint lines and rules mixed from ink
    toward ground). A one-colour look (Phosphor) turns wholly; other looks keep their map, legend and field colours,
    which carry meaning. The mode follows the palette's ground, so the Guide's Day palette is a light page.
  - The Atlas's own on-screen extras (title, label and margin ink, the cover's letters) take the palette's; the
    Guide's case and keys stay as they are.
  - The theme document is turned too, so marks drawn from the theme (the chart) follow the palette.
  - `shell/src/atlas/looks.ts` now holds `ATLAS_LOOKS` and the Atlas look extras, so tests can read them.
- **Styles screen (`views/styles`):** it picked a view by id, and the GM's and the players' Atlas share one, so
  the players' Atlas showed the GM's empty schema. It now keys the pick by scene and id.
- **A fix outside the track, told to its owner:** `SplitScreen.svelte` (PB9) set `html, body { background: #000 }`
  globally, and the shell's one bundle carried it to every players' screen, so a light look sat on black. Now it
  applies only while a split is on the page (`:has(.split)`).
